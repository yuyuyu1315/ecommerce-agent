# 电商运营 Agent 产品决策文档

> 本文档用 PAR（Problem-Action-Result）模型完整记录产品从"为什么做"到"怎么评估"的决策链路。
> 所有指标均来自真实运行（详见 `docs/rag_evaluation.md` 与 `docs/rag_evaluation.jsonl`），无编造数字。

---

## 一、Problem：业务背景与用户痛点

**目标用户**：跨境电商中小卖家（以英国在线零售为代表），SKU 数百至数千，运营团队 1~5 人。

**真实痛点**（来自 UCI Online Retail 数据集特征）：
- 商品 SKU 多、更新频繁，Excel 台账维护版本混乱，历史价格与销量无法沉淀为决策依据；
- 选品靠经验拍脑袋，缺乏"需求强度、利润空间、竞争格局、市场特征"的结构化评估；
- 定价无方法：成本加成、竞争导向、需求导向三种策略没有可执行的落地工具；
- 营销活动无节奏、无复盘，活动效果无法归因；
- 运营知识散落在文档里，新人不具备检索能力，团队经验无法沉淀复用。

**项目定位**：不做"功能堆砌的技术 Demo"，而是做一个**能回答"选什么品、定什么价、做什么活动、为什么这么建议"的数据驱动运营助手**。

## 二、Action：我做了什么

### 2.1 数据策略（本轮核心改造）

| 维度 | 方案 | 口径 |
|---|---|---|
| 数据来源 | UCI Online Retail 真实公开数据集（54 万条交易，英国在线零售 2010-12~2011-12） | 真实 |
| 商品 | 清洗（剔除退货/邮费/非商品记录）→ 聚合（SKU 去重）→ 按销售额取 Top 300 | 真实 |
| 价格/销量 | 价格取中位价，月销量 = 总销量 ÷ 覆盖月数 | 真实 |
| 分类 | 商品名关键词规则归类（9 类） | 派生（透明标注） |
| 竞品价 | 同分类价格带 P25/P50/P75 衍生 | 派生（透明标注） |
| 成本/库存 | 成本 = 售价 × 0.6（行业毛利率口径）；库存 = 月销 × 15 天 | 估算（透明标注） |
| 评价 | 数据集不含评价字段，reviews 表为空，不编造 | 缺失（如实标注） |

**为什么选 UCI Online Retail**：真实交易数据（SKU/价格/销量/市场完整），字段与项目 14 张表高度匹配，且是电商领域公开基准数据集，面试可追溯、可验证。

**数据闭环设计**：业务数据 → 评测数据 → 用户反馈 → 迭代优化 → 指标提升（见 Result）。

### 2.2 产品功能架构

三个"多角色 Agent 应用"（非堆砌式多智能体，Agent 间职责边界清晰）：
1. **选品 Agent**：基于销量/毛利/竞争/市场四维评估，输出选品建议与风险因素；
2. **定价 Agent**：结合成本与同分类价格带，输出定价建议（策略/建议价/风险）；
3. **营销 Agent**：生成活动方案与营销内容（支持 A/B 变体）；
4. **RAG 知识助手**：基于运营知识库 + 商品数据向量检索，回答运营问题并标注来源。

### 2.3 评测体系（AI 产品的核心能力）

**RAG 评测集**：30 条真实业务问答（选品 7 / 定价 7 / 营销 6 / 数据 6 / 商品查询 4），
每条记录：检索来源、延迟、Token、答案摘要（见 `rag_evaluation.jsonl`，可逐条人工复核）。

**评测驱动迭代**（V1 → V3，全部真实运行）：

| 指标 | V1 初版 | V3 加权版 | 变化 |
|---|---|---|---|
| 检索命中率 hit@4 | 66.7% | 80.0% | ↑ 13.3pp |
| 答案忠实度 | 90.0% | 90.0% | 持平 |
| 回答成功率 | 100% | 100% | — |
| 平均延迟 | 5675 ms | 5725 ms | — |
| 30 问 Token 成本 | 43938 | 41860 | ¥0.21~0.22 |

**迭代决策记录**：
- V1：单次 top-4 检索 → 300 条商品文档（描述相似度高）挤占名额，知识库方法论文档无法召回；
- V2：分类型混合检索（knowledge/product 各取 top-4）→ 商品余弦相似度仍高于知识库文档，命中率未提升；
- V3：来源加权（知识库权威来源 ×1.25 / 商品参考来源 ×1.0）→ 业务问答全量命中，命中率 80%。
- 剩余 miss 为商品精确查询类（"月销量最高/最便宜的商品"）——这是 RAG 能力边界，正确解法是 Agent 工具路由到数据库聚合查询（已在架构中标注为下一迭代项）。

## 三、Result：可回答面试官的 6 个追问

| 面试追问 | 我的答案（全部真实可验证） |
|---|---|
| 选品 Agent 准不准？拿什么测？ | 选品建议基于销量/毛利/竞争/市场四维真实数据计算，规则可复现；"准"的判定 = 建议商品的实际销量与毛利优于全库中位数（可跑数据验证） |
| 定价建议采纳率多少？ | 定价建议写入 `price_suggestions` 表，状态流转（pending→approved/rejected）即为采纳记录，可随时统计真实采纳率；当前为演示周期，采纳记录从首次真实使用起累计 |
| RAG 命中率、忠实度多少？ | 30 条真实评测：命中率 hit@4 = 80%（V3），忠实度 90%，成功率 100%，逐条明细可复核 |
| 用户拒绝原因是什么？怎么改？ | 评测失败样例已归因：① 商品文档挤占知识库 → 来源加权；② 商品精确查询超出 RAG 能力 → 规划数据库工具路由；③ 用户拒绝建议 → 建议表记录 rejected 原因字段，按原因聚类迭代 |
| Token 成本、延迟、失败率多少？ | 30 问：延迟均值 5.7s、成功率 100%、Token 4.2 万、成本约 ¥0.21；单问成本可忽略，规模化时按 AgentTask 表累计统计 |
| 如果重做，数据策略会怎么变？ | ① 接入真实卖家库存/订单数据（API/ERP）；② 评价数据补全（真实电商平台爬取或授权）；③ 价格带竞品抓取；④ 数据管线自动化（每日增量入库），核心不变的是"数据透明 + 评测先行" |

## 四、产品局限与下一迭代（诚实披露）

1. **数据边界**：当前为公开数据集演示，非真实店铺数据；成本/库存/评价为估算或缺失，已在 README 与数据脚本中透明标注；
2. **评测规模**：30 条评测集为 MVP 规模，下一迭代扩充到 100+ 条并覆盖多语言；
3. **能力边界**：聚合型问题（Top 商品、价格统计）应路由数据库查询，已列入架构规划；
4. **多智能体措辞**：当前为"多角色 Agent 应用"（选品/定价/营销/知识助手各司其职），
   未声称具备 Agent 间自主协作/规划能力——避免概念包装，保持技术诚实。
